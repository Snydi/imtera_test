## Запуск

Нужны Docker с Compose и Make.

```sh
make env
make install
```

Откройте **http://localhost:8080**. Приложение перенаправит на страницу входа. Используйте `SEED_USER_EMAIL` и `SEED_USER_PASSWORD` из корневого `.env`, с которыми был создан сид-пользователь. После входа откроются поле ссылки и список организаций.

Первый запуск скачивает образы и зависимости, создаёт `.env`, собирает фронтенд, применяет миграции, создаёт сид-пользователя и запускает сервисы с ожиданием healthcheck. Повторный запуск не пересоздаёт БД, не меняет ключ приложения и пароль существующего пользователя.

## Команды

| Команда | Действие |
| --- | --- |
| `make install` | Полная первичная настройка и запуск |
| `make remove` | Удаление локального окружения и возврат к состоянию свежего клона |
| `make up` | Запуск уже подготовленного окружения в фоне |
| `make down` | Остановка и удаление контейнеров без удаления томов |
| `make build` | Сборка PHP-образа, установка npm-зависимостей и сборка Vue |
| `make logs` | Логи сервисов; Ctrl+C завершает просмотр |
| `make migrate` | Применение миграций |
| `make lint` | Laravel Pint и проверка форматирования фронтенда Prettier |
| `make env` | Создание `.env` и заполнение пустых ключа и паролей |

`make remove` останавливает сервисы и удаляет контейнеры.

## Настройки
Единственный рабочий файл настроек — `.env` в корне, образец — `.env.example`. Compose передаёт его в Laravel через окружение контейнера. Файл `backend/.env` создавать не нужно.

## Подход к парсингу

Парсер запрашивает серверные страницы раздела отзывов карточки Яндекс Карт. Из встроенных JSON-объектов `ratingData` и `reviewResults` извлекаются средний рейтинг, точные раздельные счётчики и отзывы. Серверные страницы запрашиваются последовательно по 50 отзывов до достижения счётчика карточки либо подтверждённого окончания доступной выдачи. Аварийный предел по умолчанию — 100 страниц.

Cookies сохраняются на протяжении одного сбора. Между страницами выдерживается настраиваемая пауза. Временные сетевые ошибки и ответы 408, 425, 429 и 5xx повторяются с задержкой. Повтор уже полученной страницы, отсутствие обязательных данных, неизвестная структура отзыва и необъяснимое расхождение со счётчиком считаются ошибкой полного сбора. Частичный результат не заменяет ранее сохранённые данные.

Выбранный способ быстрее и дешевле headless-браузера, не требует отдельного Chromium-контейнера и не зависит от воспроизведения действий пользователя. По сравнению с прямым вызовом внутреннего JSON-запроса он не требует поддерживать клиентские токены и параметры внутреннего XHR. Основной риск — изменение серверной пагинации или структуры встроенного состояния.

Headless-браузер точнее повторяет работу реального пользователя и может стать резервным способом, если серверные страницы перестанут содержать данные. Его недостатки — большее потребление памяти и CPU, более медленный сбор, сложное масштабирование и необходимость поддерживать Chromium. Прямой внутренний запрос обычно быстрее HTML-парсинга, но сильнее зависит от закрытых параметров, токенов и изменений недокументированного интерфейса.

## Дополнительные требования

### 1. Устойчивость к смене формата

Парсер проверяет наличие `ratingCount`, `reviewCount`, `ratingValue`, массива отзывов и обязательных полей каждой записи, а также диапазоны рейтингов и корректность счётчиков. Пустой список при ненулевом счётчике, повтор страницы или повреждённый JSON завершают job ошибкой. Организация получает статус `failed` и текст причины, который виден в интерфейсе; исключение сохраняется стандартным механизмом failed jobs Laravel. Поэтому изменение источника не маскируется под успешный результат без отзывов.

### 2. Обоснование способа сбора

Для прототипа выбран разбор серверного HTML со встроенными JSON-данными. Он проще в эксплуатации и быстрее браузера, при этом не требует воспроизводить закрытый внутренний запрос. Строгая проверка результата ограничивает риск незаметного сохранения некорректных данных.

### 3. Масштаб и фоновая обработка

Полный сбор выполняет `RefreshOrganizationData` через очередь PostgreSQL, а не внутри HTTP-запроса. Организация хранит состояния `idle`, `queued`, `running`, `succeeded`, `failed`, процент прогресса и последнюю ошибку. Job выполняется не более трёх раз с паузами 10, 30 и 60 секунд и таймаутом 600 секунд. Для сети филиалов workers можно масштабировать независимо от Nginx и PHP-FPM, сохраняя ограниченную общую конкурентность запросов к Яндексу.

### 4. Антибан при регулярном сборе

Сейчас реализованы пауза между страницами, единый User-Agent в рамках окружения, cookies на время сбора, сетевые повторы с задержкой и отдельное сообщение для ответов 403/429. Для регулярного обновления десятков филиалов потребуются общий rate limiter, случайный jitter, экспоненциальный backoff, ограничение числа одновременных jobs и circuit breaker после серии блокировок.

При необходимости прокси должны выбираться из контролируемого пула с проверкой доступности и репутации. User-Agent следует ротировать согласованно с другими HTTP-заголовками и cookie-сессией. После признаков блокировки адрес прокси нужно временно исключать, увеличивать паузу и не продолжать агрессивные повторы. Эти механизмы для production-нагрузки пока не реализованы.

### 5. Идемпотентность и история изменений

Отзывы имеют уникальную пару `organization_id + external_id`. Повторный успешный сбор использует upsert: существующие отзывы обновляются, новые добавляются, а исчезнувшие из доступной выдачи удаляются. Рейтинг, счётчики, отзывы и время обновления изменяются в одной транзакции. При ошибке ранее сохранённое состояние остаётся доступным.

Полная история пока не хранится. Для неё планируются `parse_runs`, `organization_snapshots` и при необходимости `review_snapshots`: идентификатор запуска, время, исходные счётчики, рейтинг, статус и изменившиеся значения. Такая схема позволит показывать изменения «было → стало» и не копировать неизменившиеся данные без необходимости.

## Ограничения текущей реализации
- Эквивалентные варианты ссылки на одну карточку не приводятся к единому каноническому URL.
- Периодическое обновление по расписанию не реализовано, поэтому сервис `scheduler` отсутствует.
- История снимков и production-механизмы ротации прокси не реализованы.
- Доступность всех отзывов зависит от объёма, который Яндекс отдаёт через серверную пагинацию; неполнота или неизвестный формат завершают сбор ошибкой.
